## 0. Bus access rules (apply everywhere)

- **Every register is 16 bits wide and is accessed with 16-bit (`move.w`) reads and writes.**
  The struct is all `u16` (H:28-117). `zzwrite16` is a plain `*reg = value` (G:399-401).
- **32-bit values are written as two 16-bit writes, high word first** (`_HI` register, then `_LO`).
  `zzwrite32` writes `reg[0]` (high word on the big-endian 68k), then `reg[1]` (G:403-407). The same
  rule applies to the `ZZWRITE32` macro (G:529-531) and to SetSwitch (G:952-956). The RTG driver
  never makes a 32-bit access to a register.
- **The write to an "op" register triggers the operation.** Parameter registers only hold values,
  and the firmware keeps their last value, which is what makes write-skipping caches work (BC:4-5).
  A list of trigger registers is in §6.
- **The driver has no delays, busy-waits or barriers anywhere** except the VBlank poll (§5) and the
  WaitBlitter read fence (§6.1).
- 68060/Z3 cache: GFXData and the scratch area are ordinary card memory written by the CPU before the
  trigger. The driver relies on that memory being non-cached, or on P96's cache-mode handling
  (`BIF_CACHEMODECHANGE` is set on Z3, G:726-727). It also has an optional, compiled-out
  `DUMMY_CACHE_READ` hack that reads `0x07F00000` "for tricking the 68k cache on processors with
  occasional garbage output" (G:831-836). *(advice)* On the A4000/060, map the register window,
  GFXData and the scratch area non-cacheable and serialized, or push the cache before every trigger.

## 1. Board discovery and address map

### 1.1 Autoconfig IDs

| Variant | Manufacturer | Product | Source |
|---|---|---|---|
| Zorro II | `0x6D6E` ("mn") | `3` | G:120-122, HW:16-18 |
| Zorro III | `0x6D6E` | `4` | G:120-122, HW:16-18 |

FindCard tries Z3 first, then Z2 (G:643-644). It only accepts a ConfigDev that still has `CDF_CONFIGME`
set and is not the one already reserved (G:335-344). After that it clears `CDF_CONFIGME` to claim the
board (G:696-697). ZZTop checks the Z2 product first instead (TOP:938-951). The order does not matter
when only one board is present.

### 1.2 Bases derived from the ConfigDev

| Item | Z2 | Z3 | Source |
|---|---|---|---|
| Register base (`RegisterBase`) | `cd_BoardAddr` | `cd_BoardAddr` | G:663 |
| VRAM base (`MemoryBase`) | `cd_BoardAddr + 0x10000` | `cd_BoardAddr + 0x10000` | G:649 |
| VRAM size given to P96 (`MemorySize`) | `cd_BoardSize - 0x30000` | `0x3000000 - 0x10000` = `0x2FF0000` (about 47.9 MB) | G:650-656 |
| GFXData block (Z3 only) | n/a | `MemoryBase + 0x31F0000` = **board + 0x3200000** | G:110, 657-659 |
| Scratch/"template" area | `MemoryBase + MemorySize` = **board + BoardSize - 0x20000** | `MemoryBase + 0x3200000` = **board + 0x3210000** | G:111, 1478-1481, 1774-1788, 1994-1997 |

- The firmware addresses VRAM by **offset from `MemoryBase` (board + 0x10000)**. Every
  `blitter_src/dst`, `pan_ptr`, GFXData `offset[]` value, and the capture address, is
  `(cpu_addr - MemoryBase)` (G:981, 989, 1231, 1254, 1386, 1448, 1452, …).
- The SD-boot header says anything at or above `0x10000` in the Zorro window "falls through to
  framebuffer memory" (SDH:52-55), which confirms that VRAM starts at board + 0x10000.
- The Z3 comment "13.8 MB for Z3 (safety, will be expanded later)" (G:653) is stale. The code
  sets `0x2FF0000`.
- FindCard zeroes the GFXData struct on Z3 with `memset` (G:659).
- **UNCLEAR:** the actual `cd_BoardSize` for either variant is never hard-coded. Z2 sizes everything
  from `cd_BoardSize`. The MHI Z3 code puts buffers at VRAM offset `0x06000000`, so the Z3 window is
  larger than 96 MB (MHI:412-416).

### 1.5 Firmware version check

- `REG_ZZ_FW_VERSION` (0xC0) is a 16-bit value: **major = bits 15-8, minor = bits 7-0**
  (G:667-669, DIAG:28-33).
- The driver requires **at least 2.0**. Below that it raises `DisplayAlert(RECOVERY_ALERT)` and
  FindCard fails (G:60-61, 679-684).
- `REG_ZZ_HW_VERSION` (0x00) is read only in debug builds (G:664-666). ZZTop's register probe
  treats `fw == 0`, `fw == 0xFFFF` or `hw == 0xFFFF` as a bad bus (TOP:581-595).
- Gotcha: the struct field at 0x00 is named `fw_version` (H:29), but the enum calls it
  `REG_ZZ_HW_VERSION`. The real firmware version is at **0xC0**.

### 1.6 Init-time writes (FindCard and InitCard)

Both functions issue these writes:

1. `videocap_vmode` (**0x0E**) = `1` for an 800x600 60 Hz scandoubler, or `6` for 720x576 50 Hz
   (G:112-113, 346-354, 693).
2. Non-standard VSync feature: `USER1` (0x40) = `CARD_FEATURE_NONSTANDARD_VSYNC` (=2), then
   `SET_FEATURE` (0x60) = mode, where 0 = off, 1 = PAL, 2 = NTSC (G:356-359, H:272-277).

The source of each setting, in order:

- **ENV flags** (FindCard): `ENV:ZZ9000-VCAP-800x600`, `ENV:ZZ9000-NS-VSYNC` and
  `ENV:ZZ9000-NS-VSYNC-NTSC` (G:687-694).
- **Tooltypes** (InitCard), which override the ENV flags: `ZZ9000-VCAP-800x600`,
  `VCAP=800x600|60|60HZ|720x576|50|50HZ|bool`, `ZZ9000-NS-VSYNC`, `ZZ9000-NS-VSYNC-NTSC` and
  `NSVSYNC=NTSC|PAL|bool` (G:284-331, 361-374, 806).

InitCard then resets the blitter register cache (G:807).

## 2. Mode setting

### 2.1 Register 0x02 `REG_ZZ_MODE`: the only mode-set write

`MODE = modeline_id | (colormode << 8) | (scale << 12)`, one 16-bit write (G:893-901).

| Field | Bits (inferred from the shifts) | Values |
|---|---|---|
| modeline id | 7-0 | table below |
| colormode | 11-8 | `MNTVA_COLOR_8BIT=0`, `16BIT565=1`, `32BIT=2`, `15BIT=3` (H:22-26) |
| scale | 15-12 | `0` = 1:1, `3` = 2x doubled. These are the only two values used (G:878-888). The meaning of individual bits is **UNCLEAR** (probably H and V doubling). |

**Modeline ids** (G:838-870). These are the only resolutions the firmware is asked for:

| id | Output | id | Output |
|---|---|---|---|
| 0 | 1280x720 | 8 | 720x480 |
| 1 | 800x600 | 9 | 640x512 |
| 2 | 640x480 | 10 | 1600x1200 |
| 3 | 1024x768 | 11 | 2560x1440 (P96S names it `2560x1440@30`) |
| 4 | 1280x1024 | 16 | 640x400 |
| 5 | 1920x1080 | 17 | 1920x800 |
| 6 | 720x576 | | |

- Ids 7 and 12-15 are not used by the driver (**UNCLEAR** whether the firmware defines them).
- **Refresh rates and pixel clocks are not in the source.** The only hints are VCAP 800x600 = 60 Hz,
  720x576 = 50 Hz (G:348-352) and "2560x1440@30" (P96S).
- The firmware owns all timing. The driver ignores ModeInfo timings and reports a fixed
  `PixelClock = 100 MHz` for any accepted mode (G:1098-1127). It strips `GMF_INTERLACE` and
  `GMF_DOUBLECLOCK` (G:903-905).

**Doubled (scale = 3) modes** (G:872-891):

- A mode is doubled when `Width < 640 && Height < 480`. The firmware is then given the modeline for
  `(2W, 2H)`, so 320x200 → id 16, 320x240 → id 2, 320x256 → id 9, 400x300 → id 1, 360x288 → id 6,
  and so on.
- A mode is rejected if it is smaller than 320x200, or if (after doubling) it is not in the table.
- The comment "output as 640x480 wrapped in 800x600 sync" (G:883-884) contradicts the mode-id logic.
  **UNCLEAR** which one describes the firmware.
- P96S ships the resolutions 320x200, 320x240, 320x256, 640x480, 640x512, 720x480, 720x576, 800x600,
  1024x768, 1280x720, 1280x1024, 1600x1200, 1920x1080 and 2560x1440@30.

| Hook | Writes | Source |
|---|---|---|
| **SetGC** | Stores ModeInfo and Border. Computes colormode from `b->RGBFormat` and writes `MODE` (0x02) once. If the format or mode is unsupported it **does nothing** (no error). | G:907-935 |
| **SetDAC** | Nothing (empty) | G:813 |
| **SetClock** | Nothing | G:825 |
| **SetDisplay** | Nothing. Only remembers the state: "No firmware display-blanking register is exposed" | G:1088-1096 |
| **SetMemoryMode / SetWriteMask / SetClearMask / SetReadPlane** | Nothing | G:826-829 |

**Pitch.** CalculateBytesPerRow = `width × Bpp`, with no alignment: 8-bit = w, 15/16-bit = 2w,

### 2.3 SetPanning: the displayed framebuffer address

`offset = addr - MemoryBase` is a byte offset from board + 0x10000.

**Z2 path (registers), G:988-996:**

```
X1        (0x10) = x_offset                    ; cached write
Y1        (0x12) = y_offset                    ; cached write
X2        (0x14) = width                       ; bitmap width in pixels; cached write
COLORMODE (0x30) = pan_colormode               ; 15BIT is sent as 16BIT565 (G:187-189); cached
PAN_HI    (0x0A) = offset >> 16
PAN_LO    (0x0C) = offset & 0xFFFF             ; always written, hi then lo
```

**Z3 path (GFXData mailbox), G:979-987:**

```
gfx.offset[0] = offset; gfx.x[0] = x_offset; gfx.y[0] = y_offset; gfx.x[1] = width;
gfx.u8_user[0] = pan_colormode;  then  DMA_OP (0x5A) = OP_PAN (10)
```

- **UNCLEAR:** which PAN half latches the address. The driver always writes HI then LO. The firmware
  presumably derives the stride from `width × Bpp` and adds `y × stride + x × Bpp`. This is not stated
  in the source.
- The PAN registers are also written directly on Z3 (SetSwitch, §2.4), so the direct path works on
  both buses.

### 2.4 SetSwitch: native Amiga passthrough vs RTG (G:937-971)

**`enabled == 0`** (show the Amiga video through the ZZ9000's capture):

1. Write the PAN registers to point at the capture buffer:
   - VCAP 720x576 (default): `PAN_HI = 0x00E0`, `PAN_LO = 0x0000` (offset `0xE00000`).
   - VCAP 800x600: `PAN_HI = 0x00DF`, `PAN_LO = 0xF2F8` (offset `0xDFF2F8`, "slightly adjusted
     centering").
2. Write `*(UWORD*)(board + 0x1006) = 1` (capture mode).

The comment says the "firmware will detect that we are capturing and viewing the capture area and
switch to the appropriate video mode (VCAP_MODE)" (G:959-961).

**`enabled != 0`** (RTG):

1. Write `board + 0x1006 = 0`.
2. Re-run SetGC with the stored ModeInfo, which rewrites `MODE`.

**Pan is not restored here.** The driver relies on P96 calling SetPanning afterwards.

The return value is the previous logical state (CardData[3]).

### 2.5 Screen split (SetSplitPosition, G:2051-2080)

- `pos != 0`: `offset = VisibleBitMap->Planes[0] - MemoryBase`. If there is no visible bitmap,
  `pos` is forced to 0 and `offset` to 0.
- Z2: `BLIT_SRC_HI/LO = offset` (cached), then `SET_SPLIT_POS` (0x5E) = `pos` (the trigger).
- Z3: `gfx.offset[0] = offset; gfx.y[0] = pos; DMA_OP = OP_SET_SPLIT_POS (16)`.
- The lower screen can use the secondary palette (§3).

## 3. Palette (8-bit CLUT)

SetColorArray(start, num), G:999-1039. P96's CLUT entries are 8-bit R, G, B (`BitsPerCannon = 8`).

- Entries with `start >= 256` address the **secondary palette** (`b->SecondaryCLUT`, used for the
  split/lower screen). The source index is `(start + i) & 0xFF`. At most 256 entries are sent.
- On first use of the secondary palette, the driver enables the feature once: `USER1 (0x40) = 1`
  (`CARD_FEATURE_SECONDARY_PALETTE`), then `SET_FEATURE (0x60) = 1` (G:1007-1013, H:272-277).

**Z2 path: one entry per 4 writes to the CX block:**

```
0x1000 = (index << 8) | R           ; = xrgb >> 16, where xrgb = index<<24 | R<<16 | G<<8 | B
0x1002 = (G << 8) | B
0x1004 = 3        (primary)  or 19 (secondary)
0x1004 = 0                          ; op must be cleared after each entry
```

**Z3 path: one batch:**

```
gfx.clut1[3*i+0..2] = R,G,B for i = 0..count-1   (packed triples; clut1 starts at GFXData+92)
gfx.user[0] = start          ; raw value, may be >= 256
gfx.user[1] = count
gfx.u8_user[0] = (start >= 256)
DMA_OP = OP_SET_PALETTE (17)
```

- **UNCLEAR:** whether the firmware masks `user[0]` for the secondary case.
- Direct-colour modes do not use the palette.

## 4. Hardware sprite (mouse pointer)

P96 fields used: `MouseImage` (UWORD*), `MouseWidth`, `MouseHeight`, `Flags & BIF_HIRESSPRITE`,
`Flags & BIF_BIGSPRITE`, `XOffset/YOffset` (the pan offsets!) and `YSplit` (BI:507-558,
G:1953-2049).

### 4.1 Image (SetSpriteImage, G:1991-2029)

- `hires = BIF_HIRESSPRITE ? 2 : 1` and `big = BIF_BIGSPRITE ? 1 : 0`. The driver itself never sets
  these flags.
- The CPU copies `data_size = (MouseWidth/8) * 2 * hires * MouseHeight` bytes from
  `MouseImage + 2*hires` (UWORD units, which skips the Amiga-sprite control words: 4 bytes lores,
  8 bytes hires) into the **scratch area**. The data is Amiga hardware-sprite layout: per line, the
  plane-0 data then the plane-1 data, 2 bits per pixel (colour 0 = transparent, 1-3 = colours). The
  layout is inferred from P96's MouseImage format, not stated in this source.
- **Z2:**
  ```
  BLIT_SRC = scratch_offset   ; cached write
  X1 = b->XOffset
  X2 = MouseWidth | (big << 8)
  Y1 = b->YOffset
  Y2 = MouseHeight | ((hires-1) << 8)
  SPRITE_BITMAP (0x48) = 0    ; trigger: load the image
  ```
- **Z3:**
  ```
  gfx.offset[1] = scratch_offset
  gfx.x[0] = XOffset; gfx.x[1] = W | big<<8
  gfx.y[0] = YOffset; gfx.y[1] = H | (hires-1)<<8
  DMA_OP = OP_SPRITE_BITMAP (13)
  ```

### 4.2 Position (SetSpritePosition, G:1968-1989)

- **Z2:** `X1 = x`, `Y1 = y + YSplit` (cached), then **`SPRITE_Y (0x08) = 1`** as the trigger.
  `SPRITE_X` (0x06) is never written.
- **Z3:** `gfx.x[0] = x; gfx.y[0] = y + YSplit; DMA_OP = OP_SPRITE_XY (11)`.
- **Hotspot:** the driver never uses `MouseXOffset/MouseYOffset`. Per the comment (G:1973-1974), the
  firmware applies the P96 offset adjustment using the pan X/Y offsets passed with the image.
  **UNCLEAR** whether P96 has already subtracted the hotspot from `x,y`.

### 4.3 Colours (SetSpriteColor, G:2031-2049)

P96 passes `idx` 0-2. The firmware index is **`idx + 1`** (1-3).

- **Z2:** `USER1 = R`, `USER2 = B | (G << 8)` (cached), then `SPRITE_COLORS (0x4A) = idx + 1`
  (the trigger).
- **Z3:** the bytes of `gfx.rgb[0]` are written as **B, G, R, 0x00** at increasing addresses, then
  `gfx.u8offset = idx + 1` and `DMA_OP = OP_SPRITE_COLOR (12)`.

### 4.4 Enable and disable (SetSprite, G:1953-1966)

- The driver **always writes `SPRITE_BITMAP (0x48) = 1` and returns TRUE**, even when P96 passes
  FALSE ("Keep the legacy ZZ9000 behavior"). So `0x48 = 1` means show or enable, and `0x48 = 0`
  (Z2) means load the image.
- **UNCLEAR:** how to hide the sprite. The source contains no disable path.
- `OP_SPRITE_CLUT_BITMAP (14)` exists in the enum (H:294) but is unused.

## 5. VBlank

- `REG_ZZ_VBLANK_STATUS` (0x4C), read 16-bit: **non-zero = currently in vertical blank** (G:1131-1134).
- `WaitVerticalSync(b, end)`:
  - `end` true: spin **while** the status is non-zero, until the blank ends.
  - `end` false: spin **until** the status is non-zero.
  - Both loops are capped at 200 000 iterations (G:1129, 1136-1147).
- `GetVSyncState` returns the status directly (G:1149-1154).
- **No VBlank interrupt is used.** The board interrupts through `REG_ZZ_CONFIG` (0x04), which is
  shared by Ethernet and audio (INT6 by default, INT2 optional):
  - Read: bit 0 = Ethernet, bit 1 = audio.
  - Ack: write `8|16` for Ethernet or `8|32` for audio.
  - Ethernet mask: write `status & ~1`, re-enable with `1`.
  - Audio IRQ enable: bit 0 of 0xF4.
  - Sources: NET:100-121, 960, 1074; AHI:377-391, 428-441.
  - **The RTG driver never touches 0x04, and Prism must not either.** No VBlank bit has been seen.

## 6. Blitter

### 6.1 Execution model

- Each operation starts with **one 16-bit write to its trigger register**. The value written is often
  an argument: mask, mode or depth.
- The comment says register writes "dispatch the blitter synchronously". There is **no busy bit**.
  WaitBlitter only reads `DMA_OP` (0x5A) and `ACC_OP` (0x5C) as a "register-read fence"
  (G:814-824).
- On Z3, ZZ_AllocBitMap reads a GFXData result immediately after the `ACC_OP` write (G:1722-1724),
  which is consistent with synchronous completion.
- **Two front-ends reach the same firmware routines:**
  - **Z2:** parameter registers 0x10-0x46, then the per-op trigger register.
  - **Z3:** fill the GFXData mailbox in card memory (§6.3), then write the opcode to
    **`DMA_OP` (0x5A)**.
  - The driver uses the GFXData path whenever `CARDFLAG_ZORRO_3` is set. **UNCLEAR:** whether the Z2
    register path also works on a Z3 board. The MODE, PAN, CX, sprite-enable, feature and VBlank
    registers are used on both.

### 6.2 Register file (offsets from the board base, all 16-bit)

| Off | Name | Role in the RTG driver |
|---|---|---|
| 0x00 | HW_VERSION | read (debug) |
| 0x02 | MODE | §2.1 |
| 0x04 | CONFIG | IRQ status/ack (§5), **do not touch** |
| 0x06 | SPRITE_X | unused |
| 0x08 | SPRITE_Y | **trigger:** sprite position (Z2) |
| 0x0A/0x0C | PAN_HI/LO | display start offset |
| 0x0E | VCAP_MODE | scandoubler output mode 1 or 6 |
| 0x10/0x12 | X1/Y1 | dst x/y (or line start, pan x/y, sprite pos) |
| 0x14/0x16 | X2/Y2 | width/height (or line dX/dY, sprite W/H) |
| 0x18 | ROW_PITCH | destination pitch (units: see §6.4) |

  (G:1719-1731, 1750-1752).

### 6.3 GFXData mailbox layout (Z3; `#pragma pack(4)`, H:326-340)

Base: board + 0x3200000. The CPU writes it big-endian, as ordinary 68k stores.

| Off | Field | | Off | Field |
|---|---|---|---|---|
| 0 | `u32 offset[0]` (DST) | | 48 | `u8 u8_user[8]` ([0]=colormode, [1]=drawmode, [2]=line pattern offset, [3]=line pad) |
| 4 | `u32 offset[1]` (SRC) | | 56 | `u8 op` (unused) |
| 8 | `u32 rgb[0]` (fg) | | 57 | `u8 mask` |
| 12 | `u32 rgb[1]` (bg) | | 58 | `u8 minterm` |
| 16 | `u16 x[4]` | | 59 | `u8 u8offset` |
| 24 | `u16 y[4]` | | 60 | `u32 u32_user[8]` |
| 32 | `u16 user[4]` | | 92 / 860 / 1628 / 2396 | `u8 clut1..clut4[768]` |
| 40 | `u16 pitch[4]` ([0]=DST, [1]=SRC) | | 3164 | end |

Offsets in this table are computed from the struct definition, not read from the source.
**UNCLEAR:** how the little-endian ARM reads multi-byte fields. SetSpriteColor alone stores
`rgb[0]` byte-by-byte as B,G,R,0 (G:2037-2040), which hints that the firmware swaps fields
individually.

### 6.4 Per-operation recipes

`DST = r->Memory - MemoryBase` and `BPR = r->BytesPerRow`. **Pitch units differ by operation, so
watch them:**

- **longwords (BPR >> 2):** fill, invert, copy, line, P2C, P2D destination.
- **bytes:** template and pattern destination, template source, P2C/P2D source.

Before any operation, a format that maps to `NO_USE` falls back to P96's `...Default` routine. For
32-bit formats the mask is forced to 0xFF (`direct_color_mask`, G:191-193) in fill, invert, template,
pattern and line, but **not** in BlitRect.

**FILLRECT** (G:1223-1281)

- Z2:
  ```
  DST = DST
  RGB = color
  ROW_PITCH = BPR>>2
  COLORMODE = cm          ; high byte 0
  X1 = x, Y1 = y, X2 = w, Y2 = h
  FILLRECT = mask
  ```
- Z2 shortcut: if `min(w,h) < 6 && max(w,h) < 32`, use the software fallback instead (G:1245-1253).
- Z3: `offset[0] = DST`, `pitch[0] = BPR>>2`, `u8_user[0] = cm`, `mask`, `rgb[0] = color`,
  `x[0] = x`, `x[1] = w`, `y[0] = y`, `y[1] = h`; then `DMA_OP = 2`.
- `color` is P96's value passed through raw. The driver's own CPU line path takes 8-bit pens from
  bits 31-24 and 16-bit colours from bits 15-0 (G:1164, 1169, 1190, 1201), consistent with P96
  replicating the pen across the longword.

**INVERTRECT** (G:1283-1331)

- Z2: same as fill without RGB: `DST`, `ROW_PITCH = BPR>>2`, `COLORMODE = cm`, `X1/Y1/X2/Y2`,
  then `INVERTRECT = mask`. Same small-rect shortcut.
- Z3: `DMA_OP = 9`.

**COPYRECT, BlitRect within one bitmap** (G:1334-1392)

- Z2:
  ```
  Y1 = dy, Y2 = h, Y3 = sy
  X1 = dx, X2 = w, X3 = sx
  ROW_PITCH = BPR>>2
  COLORMODE = cm | mask<<8
  SRC = DST = DST
  COPYRECT = 1
  ```
- SRC_PITCH is not written. **UNCLEAR:** the firmware presumably uses ROW_PITCH for the source.
- Z3: `offset[0] = offset[1] = DST`, `pitch[0]`, `x[2]/y[2] = src`, `x[0]/y[0] = dst`,
  `x[1]/y[1] = w/h`, `u8_user[0] = cm`, `mask`; then `DMA_OP = 3`.
- "Source and destination rectangle may be overlapping; a proper copy operation shall be performed
  in either case" (G:1372). The firmware handles overlap.

**COPYRECT, NoMaskComplete with two bitmaps and a minterm** (G:1395-1457)

- Z2:
  ```
  Y1 = dy, Y2 = h, Y3 = sy
  X1 = dx, X2 = w, X3 = sx
  COLORMODE = cm | minterm<<8
  SRC_PITCH = rsBPR>>2, SRC = rs - MemoryBase
  ROW_PITCH = rtBPR>>2, DST = rt - MemoryBase
  COPYRECT = 2
  ```
- Z3: the same fields plus `pitch[1]` and `minterm`; then `DMA_OP = 4`. The minterm uses
  graphics.library blitter minterm encoding (G:1429).

**FILLTEMPLATE, BlitTemplate** (G:1459-1523)

1. The CPU copies `t->BytesPerRow * h` bytes from `t->Memory` into the scratch area.
2. Z2:
   ```
   DST = DST
   SRC = scratch
   RGB = FgPen, RGB2 = BgPen
   SRC_PITCH = t->BytesPerRow        ; bytes
   ROW_PITCH = BPR                   ; bytes!
   COLORMODE = cm | DrawMode<<8
   X1 = x, Y1 = y, X2 = w, Y2 = h, X3 = t->XOffset
   FILLTEMPLATE = mask
   ```
3. Z3: `pitch[0] = BPR` (bytes), `pitch[1] = t->BPR`, `x[2] = XOffset`, `rgb[0..1]`,
   `u8_user[0..1] = cm, DrawMode`, `mask`; then `DMA_OP = 5`.

**Pattern, BlitPattern** (G:1525-1592)

1. Reject if `Size > 15`.
2. The CPU copies `2 << Size` bytes (16-bit-wide pattern, `1 << Size` rows) into the scratch area.
3. Z2:
   ```
   DST = DST
   SRC = scratch
   RGB = Fg, RGB2 = Bg
   USER1 = mask
   ROW_PITCH = BPR                   ; bytes
   COLORMODE = cm | DrawMode<<8
   X1, Y1, X2, Y2
   X3 = XOffset, Y3 = YOffset
   FILLTEMPLATE = (1<<Size) | 0x8000   ; bit 15 = pattern
   ```
4. Z3: `user[0] = 1<<Size`, `y[2] = YOffset`, `mask` in GFXData; then `DMA_OP = 6`.

**DRAWLINE** (G:1594-1690)

- Solid lines (DrawMode 0, LinePtrn 0xFFFF, mask 0xFF) with `dY == 0` or `dX == 0` never reach the
  line engine:
  - Z2: the CPU draws them directly into VRAM.
  - Z3: they become a 1-pixel FILLRECT.
- Z2:
  ```
  DST = DST
  ROW_PITCH = BPR>>2
  COLORMODE = cm | DrawMode<<8
  RGB = Fg, RGB2 = Bg
  X1 = X, Y1 = Y, X2 = dX, Y2 = dY
  USER1 = Length
  X3 = LinePtrn
  Y3 = PatternShift | (pad<<8)
  DRAWLINE = mask
  ```
- Z3: `x[0..1] = X, dX`, `y[0..1] = Y, dY`, `user[0] = Length`, `user[1] = LinePtrn`,
  **`user[2] = (PatternShift<<8) | pad`**. This byte order is the opposite of the Z2 `Y3` packing.
  Also `u8_user[1..3] = DrawMode, PatternShift, pad`, `rgb[0..1]` and `mask`; then `DMA_OP = 1`.

**P2C, planar to 8-bit chunky** (G:1763-1849)

1. `line_size = (w >> 3) + 2` bytes. The "+2" padding keeps the firmware's source-wrap check from
   firing (G:393-397).
2. For each plane `i < Depth`, the CPU copies `h` rows of `line_size` bytes, starting at
   `Planes[i] + y*BytesPerRow + (x >> 3)`, into `scratch + i*line_size*h`.
3. Special plane pointers:
   - `0xFFFFFFFF`: the slot is filled with 0xFF.
   - `NULL`: the slot is skipped (contents undefined) and the plane's bit is cleared in `zz_mask`.
4. Z2 fallback: if `line_size*h*Depth > 0xFFFF` (the 64 KB scratch area), use the software default.
5. Z2 writes:
   ```
   DST = DST
   ROW_PITCH = BPR>>2
   COLORMODE = cm(r->RGBFormat) | minterm<<8
   SRC = scratch
   SRC_PITCH = line_size
   X1 = x & 7, X2 = dx, Y2 = dy, X3 = w, Y3 = h
   USER2 = zz_mask
   P2C = mask | Depth<<8
   ```
6. Z3: `offset[0..1]`, `pitch[0] = BPR>>2`, `pitch[1] = line_size`, `mask`, `minterm`, `x[0] = x&7`,
   `x[1] = dx`, `x[2] = w`, `y[1] = dy`, `y[2] = h`, `user[0] = zz_mask`, `user[1] = Depth`; then
   `DMA_OP = 7`. The colormode byte is not set on Z3.

**P2D, planar to direct colour through a 256-entry LUT** (G:1851-1951)

1. `line_size = ((x & 7) + w + 7) >> 3`. This is unpadded, unlike P2C.
2. The CPU first copies `clut->Colors` (256 ULONGs = 1024 bytes) to the scratch area, then the planes
   after it, as in P2C.
3. `RGB = clut->ColorMask`.
4. Z2 fallback if `1024 + planes > 0xFFFF`.
5. The registers are as in P2C, except that `COLORMODE = cm(r->RGBFormat) | minterm<<8` and the
   trigger is `P2D = mask | Depth<<8`. Z3: `DMA_OP = 8` with `rgb[0] = ColorMask` and
   `u8_user[0] = cm`.

### 6.5 Register shadowing (the "blitter cache")

- Many parameter writes are skipped when the value equals the last one written, because "the
  firmware keeps the latest register values" (BC:1-6):
  - **Per-function statics:** `writeBlitterSrcOffset`, `DstOffset`, `RGB`, `DstPitch`, `ColorMode`,
    `X1-3` and `Y1-3` (G:409-525).
  - **Board-keyed `BlitterRegisterCache`:** `RGB2`, `USER1`, `USER2` (BC:13-81, G:442-461). It is
    invalidated when the register base changes, and reset in InitCard (G:807).
- **SRC_PITCH is never skipped.** `blitter_cache_src_pitch_write_needed` always returns 1 and clears
  its valid bit, and the unit test asserts "same src pitch still writes" (BC:61-68,
  `rtg/tests/register_cache_test.c:30-39`). **UNCLEAR** why. Presumably the firmware modifies it, or
  it aliases something.
- Triggers, `PAN_HI/LO`, `SET_SPLIT_POS` and the sprite triggers are always written.
- **Hazards for anyone copying this design:**
  - The statics start at 0, except ColorMode, which starts at `MNTVA_COLOR_32BIT` (G:472). The driver
    therefore assumes power-on register contents. If the firmware's value differs, the first write of
    that value is skipped.
  - `apply_nonstandard_vsync_settings` and the secondary-palette enable write USER1 outside or inside
    the cache inconsistently (G:357 raw, G:1009 cached). This is safe only because InitCard resets
    the cache afterwards.
  - Any other software that writes 0x10-0x46 desynchronises the shadow.
  - *(advice)* Keep one per-board shadow struct, initialise it by writing every register once at init,
    and add an invalidate call.

## 7. Pixel formats and endianness

| P96 RGBFormat (value) | MNTVA colormode | Memory layout P96 uses | Source |
|---|---|---|---|
| RGBFB_NONE (0) / RGBFB_CLUT (1) | 0 (8BIT) | 1 byte pen | G:156-158 |
| RGBFB_B8G8R8A8 (9) | 2 (32BIT) | bytes **B,G,R,A**, i.e. a little-endian `0xAARRGGBB` | G:166 |
| RGBFB_R5G6B5 (10) | 1 (16BIT565) | **big-endian** 565: `RRRRRGGG GGGBBBBB` | G:167 |
| RGBFB_R5G5B5 (11) | 3 (15BIT) | big-endian 555 | G:168 |
| everything else (24-bit, ARGB, ABGR, RGBA, PC/byte-swapped 16-bit, YUV) | `NO_USE` (255) | software fallback | G:159-177 |

- The comment says these are "the formats the firmware/video formatter interprets natively… the
  firmware only has one 32-bit mode and one RGB555 mode" (G:130-140).
- `GetCompatibleFormats` returns the full set for any supported format (G:1081-1086).
- 15-bit is a separate scan-out colormode in `MODE`, but SetPanning sends it as 565 for addressing
  (G:187-189).
- The memory layouts are P96's standard definitions. The source only names the formats, so any byte
  swapping the firmware does for the big-endian 16-bit modes is internal to it.

## 8. Gotchas and notes from the source

1. Firmware below 2.0 is refused (G:60-61, 679-684).
2. Z2 and Z3 use two different command paths: registers vs the GFXData mailbox plus `DMA_OP`. They
   share firmware routines but have different argument packing. Examples: the DrawLine pattern-byte
   order; P2C sets no colormode on Z3.
3. Pitch units differ between operations (§6.4). Template and pattern use bytes; everything else uses
   longwords.
4. Z2 has only 64 KB of scratch. P2C and P2D fall back to software above that. Z2 fill and invert fall
   back below 6x32 pixels. Z2 solid horizontal and vertical lines are drawn by the CPU.
5. Template, pattern, P2C, P2D and the sprite image all share **one** scratch buffer. There is no
   locking beyond the synchronous model.
6. `SetSprite` ignores its argument and always enables the sprite. No hide path exists.
7. `SetDisplay` cannot blank the display (there is no register for it). `SetDAC`, `SetClock` and the
   planar-memory hooks are empty.
8. `SetSwitch(1)` restores MODE but not PAN.
9. The capture buffer at VRAM `0xE00000` overlaps the P96 VRAM range (§1.4).
10. The Z3 `MemorySize` comment is stale (§1.2). The space between `0x2FF0000` and `0x31F0000` (VRAM
    offsets) is claimed by nobody.
11. The struct field at 0x00 is named `fw_version`, but the real firmware version is at 0xC0.
12. The AHI driver has a FIXME saying its buffer placement is tied to the RTG scratch address
    (AHI:588).
13. The "output as 640x480 wrapped in 800x600 sync" comment contradicts the mode-id mapping (§2.1).
14. `DUMMY_CACHE_READ` is an optional cache hack for "occasional garbage output" (G:831-836).
15. Scanline effects are active only in AGA scandoubled modes and RTG modes below 350 lines
    (README:237-239, ZZScanlines.c:19-20). The scanline state survives soft resets (TOP:956-958).

## 9. Minimal mode-set recipes (register path, as the driver's Z2 code does it)

`R = cd_BoardAddr`. Every access is `move.w`. `X` is the framebuffer's byte offset from
`R + 0x10000`, and must lie in allowed VRAM (§1.4). The framebuffer pitch is `width × Bpp`, with no
padding.

**A. Firmware check (once).**
`v = R[0xC0]`. Require `v >= 0x0200` (major 2, minor 0).

**B. 640x480, 8-bit CLUT.**

```
R+0x1006 = 0                 ; leave capture/passthrough
R+0x02   = 0x0002            ; mode 2 | color 0<<8 | scale 0<<12
for i in 0..255:             ; palette (CX block)
    R+0x1000 = (i<<8) | red[i]
    R+0x1002 = (green[i]<<8) | blue[i]
    R+0x1004 = 3
    R+0x1004 = 0
R+0x10 = 0                   ; X1  pan x
R+0x12 = 0                   ; Y1  pan y
R+0x14 = 640                 ; X2  width in pixels
R+0x30 = 0                   ; COLORMODE 8-bit
R+0x0A = X >> 16             ; PAN_HI
R+0x0C = X & 0xFFFF          ; PAN_LO
; framebuffer: 640 bytes/row x 480 rows at R+0x10000+X
```

**C. 800x600, 16-bit RGB565 (big-endian pixels).**

```
R+0x1006 = 0
R+0x02   = 0x0101            ; mode 1 | color 1<<8
R+0x10 = 0; R+0x12 = 0; R+0x14 = 800; R+0x30 = 1
R+0x0A = X >> 16; R+0x0C = X & 0xFFFF
; framebuffer: 1600 bytes/row x 600 rows
```

For 32-bit BGRA, use color 2 (`MODE = id | 0x0200`, `COLORMODE = 2`) and a pitch of `4 × width`.

For a doubled 320x240 screen, use `MODE = 0x3002` (id 2 for the 640x480 output, scale 3). In the pan
sequence, X2 is the bitmap width (320).

**D. Back to native Amiga video (passthrough via capture).**

```
R+0x0A = 0x00E0; R+0x0C = 0x0000   ; or 0x00DF / 0xF2F8 if VCAP_MODE (0x0E) = 1 (800x600)
R+0x1006 = 1
```

To return to RTG, write `R+0x1006 = 0`, then redo B or C (MODE **and** the pan writes).

**Optional, once at init.**

- `R+0x0E = 6` (720x576 50 Hz scandoubler) or `1` (800x600 60 Hz).
- Non-standard VSync: `R+0x40 = 2`, then `R+0x60 = 0/1/2` (off / PAL / NTSC).

**UNCLEAR for these recipes:**

- Whether X1/Y1/X2/COLORMODE must precede PAN on a Z3 board. The Z3 driver uses `OP_PAN` instead,
  but writes PAN_HI/LO directly in SetSwitch.
- Whether the firmware needs any settling time after a MODE write. The driver waits for nothing.
