# Z3660 RTG: hardware programming reference for Prism

The Z3660 is a 68060 accelerator for the A4000 with a Zynq SoC; the SoC's
ARM firmware provides an RTG framebuffer on its HDMI output. The firmware
is a fork of the MNT ZZ9000's and keeps its meanings (the MODE word, colour
modes, the GFXData mailbox), but not its bus ABI.

Derived from the Z3660's open sources, [shanshe/Z3660](https://github.com/shanshe/Z3660)
at `25587f5` (2026-08-23), GPL-3.0-or-later: the Picasso96 driver
`Z3660.card` ("Z3660 Graphics Card Driver based on MNT ZZ9000 rev 1.13";
ZZ9000.card (C) 2016-2023 Lukas F. Hartmann / MNT Research GmbH, (C) 2021
Bjorn Astrom; the Z3660 changes by shanshe) and the firmware it talks to.
Anything the sources do not settle is marked **UNCLEAR**; advice that is not
a fact from the source is marked *(advice)*.

## 0. Bus access rules

- **Registers are 32-bit words from `0x100`** (RH:28 onwards), at the board
  base. The firmware decodes the low 2 MB of the window and hands every
  register write below `0x2000` to its handler as the **whole aligned
  longword** (R:561-572). Write registers with aligned `move.l`; a 16-bit
  HI/LO pair as on the ZZ9000 never composes.
- **The write to a trigger register starts the operation**; parameter
  registers just hold values (R:1046 PAN, R:1102 MODE, R:1125 SPRITE_X/Y).
- Reads that matter here: `FW_VERSION` (`0x1A0`, R:793:
  `major << 8 | minor`) and `VBLANK_STATUS` (`0x17C`), which the FPGA
  answers itself (R:828-829).

## 1. Identity and windows

| What | Value | Source |
|---|---|---|
| AutoConfig | manufacturer `0x144B` (5195), product `1`, Zorro III, 128 MB, with `autoconfig_rtg YES` | G:447 |
| Firmware check | `FW_VERSION >> 8 == 1`, minor `>= 3` (firmware 1.03 or newer) | G:491, G:543 |
| Registers | board base + `0x100` ... | RH |
| VRAM | board base + `0x200000`, 46 MB (`0x3000000 - 0x200000`) | G:124, G:511 |
| GFXData mailbox | board base + `0x3200000`, above VRAM | G:125 |
| Template / sprite staging | board base + `0x3210000` | G:126 |

Below `0x200000` the window also holds the piscsi mailbox and the SCSI boot
ROM; nothing in this document writes there.

With `autoconfig_rtg NO` the board is still at `0x10000000` but there is no
ConfigDev; Z3660.card then adds one itself (G:448-483). **This driver does
not**: a probe on Auto must not touch a fixed address on a machine that has
not said it has the card *(advice)*. AmigaOS presets use `autoconfig_rtg YES`.

## 2. Modes

A mode is one write to `MODE` (`0x100`): `id | colour << 8 | scale << 12`
(R:1102, G:1530). The firmware ignores a write that repeats the current
triple (R:1102). `ORIG_RES` (`0x18C`) = `w << 16 | h` is written just
before it (G:1529).

Firmware mode ids (VM:4 onwards; timings in V:103-126):

| id | size | id | size |
|---|---|---|---|
| 0 | 1280x720 | 10 | 1600x1200 |
| 1 | 800x600 | 11 | 2560x1440 (30 Hz) |
| 2 | 640x480 | 12-15 | 720x576 / 720x480, non-standard vsync |
| 3 | 1024x768 | 16 | 640x400 |
| 4 | 1280x1024 | 17 | 1280x800 |
| 5 | 1920x1080 60 Hz | 18 | 1920x1200 |
| 6 | 720x576 50 Hz | 19 | 1600x900 |
| 7 | 1920x1080 50 Hz | 20 | 1680x1050 |
| 8 | 720x480 | 21 | 1366x768 |
| 9 | 640x512 | 22 | CUSTOM (timings through `0x200`/`0x204`) |

Up to id 11 they are the ZZ9000's; from 16 on they differ from the ZZ9000's
(where 16 = 640x400 too, but 17 = 1920x800). Z3660.card itself programs
every mode as CUSTOM from Picasso96's monitor timings (G:1503-1527), except
320x200/240/256, which it shows doubled in the fixed 640x400/480/512 modes
(G:1444-1456). A driver without timings uses the fixed ids.

Colour modes (G:155-177): `0` CLUT8, `1` RGB565 (big-endian, `PF_RGB565BE`),
`2` 32-bit B,G,R,A (`PF_BGRA32`), `3` RGB555 big-endian. No 24-bit mode.
Rows are unpadded: `width * bytes per pixel` (G:1744).

**Scale** `3` doubles both axes: SetGC uses it for anything under 640 wide
and under 400 high (G:1559-1567), with ORIG_RES = the doubled size.

**32-bit has a lower limit than the mode table.** On an A4000D (firmware
1.03 BETA 21, FPGA `0xAB000103`) 32-bit modes up to a 108 MHz pixel clock
show right on the HDMI output: 1024x768 (65 MHz), 1600x900 (93 MHz, rows
of 6400 bytes) and 1280x1024 (108 MHz). 1680x1050 (114 MHz), 2560x1440
(146 MHz at 30 Hz), 1920x1200, 1920x1080 and 1600x1200 come out
line-doubled: the top half of the picture, each row shown twice, and
2560x1440 only right in the middle. So the limit follows the pixel clock,
not the row length. At 8, 15 and 16 bits every mode tried is right, up to
1600x1200 (161 MHz) and 2560x1440. The firmware asks for no doubling
(scale 0 gives vdiv 1, V:1227-1276), so the limit is in the scan-out path.
The Z3660's CHANGES.md says the same of big modes: "32 bit video mode is
limited to 30 Hz", and the Z-turn's HDMI shows 16 bits anyway. Pixel
clocks per mode: V:103-126.

## 3. The mailbox (GFXData)

The same `#pragma pack(4)` struct as the ZZ9000's (FH:573):

| Offset | Field | Offset | Field |
|---|---|---|---|
| 0, 4 | `offset[0]`, `offset[1]` | 48-55 | `u8_user[8]` (`[0]` = colour mode) |
| 8, 12 | `rgb[0]`, `rgb[1]` | 56-59 | `op`, `mask`, `minterm`, `u8offset` |
| 16-22 | `x[4]` | 60-91 | `u32_user[8]` |
| 24-30 | `y[4]` | 92 | `clut1[768]` |
| 32-38 | `user[4]` | | |
| 40-46 | `pitch[4]` | | |

The 68k writes it big-endian; the firmware swaps what it reads (D). An
operation runs when its number is written to `BLITTER_DMA_OP` (`0x180`).
Op numbers (FH:588): 1 DRAWLINE, 2 FILLRECT, 3 COPYRECT, 4 COPYRECT_NOMASK,
5 RECT_TEMPLATE, 6 RECT_PATTERN, 7 P2C, 8 P2D, 9 INVERTRECT, **10 PAN,
11 SPRITE_XY, 12 SPRITE_COLOR, 13 SPRITE_BITMAP**, 14 SPRITE_CLUT_BITMAP,
16 SET_SPLIT_POS, **17 SET_PALETTE**. Z3660.card takes this path for every
Zorro III board (G:1683, G:1720, G:2579, G:2607, G:2636); the register forms
are its Zorro II branches.

The mailbox is ordinary card memory; keep a copyback cache from holding it
when the op is written *(advice: the ZZ9000 driver's `CacheClearU()`)*.

## 4. Display start (PAN, op 10)

`offset[0]` = VRAM offset of the bitmap, `x[0]`, `y[0]` = the view's origin
in it, `x[1]` = the bitmap's width in pixels, `u8_user[0]` = colour mode
with 15-bit given as 565 (G:1683-1690). The firmware shows
`offset[0] + x[0] << cm + y[0] * (x[1] << cm)` (D:287-299). `cm` is a shift:
0, 1 or 2.

## 5. Palette (op 17)

`user[0]` = first index, `user[1]` = count (at most 256), `u8_user[0]` = 0
for the primary palette, `clut1[]` = R,G,B bytes from index `user[0]`
(G:1720-1730, D:314-330).

## 6. Hardware sprite (ops 11-13, register `0x174`)

- **Image** (op 13): `offset[1]` = where the image is, as a VRAM offset
  (G:2607: `Z3_TEMPLATE_ADDR`, i.e. board + `0x3210000`); `x[0]`,`y[0]` = hot
  spot offset; `x[1]` x `y[1]` = size; `x[2]` = doubled, `y[2]` = hires
  (D:236-262). Rows of `w / 8` bytes of plane 0 then `w / 8` of plane 1, MSB
  = leftmost pixel; pen = plane0 + 2 x plane1 (V:1283-1330). The firmware's
  sprite is at most **32x48** (V:62).
- **Colours** (op 12): `u8offset` = pen 1-3, `rgb[0]` = the bytes B,G,R,0 in
  memory (the ARM reads them as `0x00RRGGBB`); `0xff00ff` is the
  firmware's transparent key and is turned into `0xfe00fe` (D:278-285,
  G:2631-2656). Pen 0 is transparent.
- **Position** (op 11): `x[0]`,`y[0]`; ignored while the sprite is hidden
  (D:224-233).
- **Show / hide**: write `1` / `2` to `SPRITE_BITMAP` (`0x174`, R:1135).
  Z3660.card writes 1 on every `SetSprite` (G:2553-2566).

## 7. Vertical blank

`VBLANK_STATUS` (`0x17C`) reads nonzero during vertical blank. Z3660.card
bounds both waits at 200000 reads (G:1845-1864).

## 8. Not in this document yet

The monitor switch (CIA-B lines, `MONITOR_SWITCH` `0x318`) and the blitter
ops (1-9) are the driver's later parts; their facts go here with them.
